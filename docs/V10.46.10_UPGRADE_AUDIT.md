# SoloHost Browser v10.46.10 — audit, fixes, and verification

## Scope and baseline

- The checked-out application identified itself as package version **10.46.9**. The root README and Dockerfile still said **10.35.0**.
- The repository checkout is the source tree; no `.zip` source archive was present. The baseline tracked inventory contained **395 files**. The application is a Node.js/Express service with a Playwright Chromium engine and sanitized DOM Bridge display, plus an optional HTTP proxy path. There is no separate native source archive to extract.
- Reviewed package metadata and scripts, README, Dockerfile and both Compose/configuration pairs, application routes, browser engine and DOM Bridge, Browser Agent and its task recovery, AI adapter/provider wiring, Feedback Hub service/client, architecture notes, and current/archived regression tests.
- Package dependency is Playwright **1.51.1**; application package version after the upgrade is **10.46.10**.

## Website display through the user UI (DOM Bridge)

The target pages were navigated from the actual SoloHost Browser canvas address bar and inspected in its static DOM Bridge display. This is distinct from inspecting the target page directly in Chromium. Before the fix, the React docs UI showed a very large purple React logo on a dark background, a broken image, and none of the expected page layout/content. After the CSP fix and server restart, the same app UI showed the React header, correctly sized logo, hero title, descriptive text, and action buttons on the page's light background. The same UI displayed `example.com` with its document icon, multilingual explanatory text, and Learn more link. App health returned HTTP 200 with `ready: true` and version `10.46.10`.

The source explains the React failure: the sanitizer injects `<base href="https://react.dev/...">` into the snapshot, but `/api/browser/sessions/:id/view` is served from the SoloHost origin with `base-uri 'self'`. The browser therefore cannot use the page-origin base URL in this iframe; root-relative stylesheets and image URLs resolve against the app origin instead. The CSP now allows the current page's origin (and no other site origin) for `base-uri`, retaining `default-src 'none'` and `script-src 'none'`. The before/after verification used only the app's user-facing UI and confirms the layout is restored for React; it is not evidence that all websites or resources work.

The 12 JPEGs in `upgrade-evidence/` were captured earlier from the Playwright engine/API, not from the user-visible DOM Bridge UI. They are retained only as backend/API diagnostics and must not be interpreted as proof that those six sites displayed correctly in the app UI. They are not used to substantiate the layout finding or its resolution. No additional target websites were inspected after the user's clarification to use the app UI only. A post-fix React UI screenshot is supplied separately with the delivery.

## AI Panel message formatting

The supplied Vietnamese sample was entered through the actual AI Panel chat UI. Its `<br>` separators rendered as separate lines and `&quot;` displayed as quotes, with bullets intact. The formatting regression now exercises that exact content shape, ordinary newline/Markdown input, encoded and raw HTML payloads, and an unsafe URL scheme. All content is parsed from text and escaped before being written to the message DOM; no raw AI HTML is enabled. A live model response could not be tested because no provider is configured.

The AI Kernel now generates its app knowledge dynamically from `package.json` and the Feedback Hub module's defaults/runtime environment. It contains current version, verified major features and limits, short user guidance (including Agent provider setup, Continue, and `/new`), Hub ID/base URL/transport status, and explicit rules never to ask ordinary users for Hub credentials. Hub URLs are sanitized before model context; tokens are never included. The AI service's knowledge budget was raised from 2,500 to 4,000 characters, and the regression ensures all current knowledge fits. The offline answer for Feedback Hub questions reads the same live server configuration.

## Browser Agent and AI Panel

- Existing `test/agent-task-not-found-fix.js` passed, exercising task hydration/rebinding and continuation. Existing Browser Agent unit tests in `npm test` passed, including action and report behavior.
- `test:e2e` is not a usable full UI E2E suite: its own source exits with `SKIP` because its client-DOM harness was retired in v10.8 and requests a backend task API harness on a running SoloHost/WebKit instance.

- AI knowledge remains generated from the current `package.json` and source-backed `app-adapter.js` capabilities. It distinguishes desktop/mobile profiles and accurately states that Feedback Hub ingestion stays disabled until the token is configured as a server-side deployment secret and the Hub base is a verified HTTPS endpoint. Existing English/Vietnamese input regression passed. No unsupported Agent capability is claimed.

## Feedback Hub and privacy

- The supplied Hub ID is `SHFH-CANNOI-0905428801` and its public base URL is `http://14.176.78.46:8090`. An ingest token was supplied in a follow-up conversation; it was deliberately not transcribed, logged, copied to source/docs/archive, or configured in the environment. No secret value is present in this report or package. No verified HTTPS endpoint or API contract was supplied.
- The existing HTTP default URL remains unchanged. Because bearer tokens must not be sent over HTTP and a secure endpoint/contract is unavailable, ingestion remains fail-closed. The live config endpoint reported `enabled: false`, and a live submission attempt returned a configuration error without contacting the Hub. Configure the token only as a deployment secret (`SHFH_INGEST_TOKEN`) after a verified HTTPS Hub base is available via `SHFH_HUB_URL`.
- Read-only sync/API behavior and notice-read authentication were not verified against the real Hub contract. Notice-read intentionally does not receive the ingest credential under the “ingestion endpoint only” restriction. Configure the real token via `SHFH_INGEST_TOKEN` and a verified HTTPS Hub base via `SHFH_HUB_URL` before enabling authenticated submissions.
- The feedback endpoint forwards only event/type/rating/message/anonymous ID/locale plus server-owned app metadata. It does not forward browser history, cookies, passwords, tokens supplied in the request, or arbitrary request fields.

## Inventory, packaging, and remaining limitations

The source checkout was inventoried as the application itself; no input ZIP existed in the repository. A complete **416-entry** `SoloHost-Browser-v10.46.10.zip` was regenerated as a session artifact after the AI Kernel update, with source, tests, configuration, this audit report, and evidence. The archive passed CRC verification and includes required runtime files; it excludes `.git`, `node_modules`, all `.env*` files, runtime `data`, databases, and ignored `artifacts`. The final Docker image built and passed a container health smoke test, returning `ok: true`, `ready: true`, and version `10.46.10`.

Not fully verified: all browser feature permutations, account authentication/session persistence across restarts, actual Agent permissions/cancellation with a configured model, mobile UI on a physical device, public Hub API integration, Docker/SoloHost deployment behavior beyond Compose validation and the successful image health smoke test, and rendering across the full international web. The supported image is Chromium/Playwright; no alternative browser engine was installed or tested here.
